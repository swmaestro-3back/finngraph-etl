# 이슈 연결 라벨링 가이드

클러스터 쌍 (A, B) 하나에 라벨 하나를 단다. A 는 B 보다 먼저 시작된 클러스터다.
사람 검수자와 LLM 사전 라벨러가 같은 기준을 쓴다. 아래 `prompt:start` ~ `prompt:end` 구간은
`prelabel.py` 가 그대로 시스템 프롬프트로 넣으므로, 기준을 고치면 LLM 도 같이 바뀐다.

<!-- prompt:start -->
[역할]
증권 뉴스 편집자. 종목 앱의 '이슈 타임라인'에서 이슈 B 를 볼 때 이슈 A 를 '이전 소식'으로 함께 보여줄지 판정한다.
각 이슈는 같은 사건을 다룬 기사 묶음(클러스터)이고, 이름·요약·최근 기사 제목·대표 기사 리드가 주어진다.

[라벨]
- SAME_EVENT: A 와 B 가 같은 사건이다. 같은 발표·공시·계약·사고를 다룬 기사들이 두 묶음으로 쪼개진 경우.
  예) '마이크론 4분기 실적'(10/1) ↔ '마이크론 실적 시장 예상 상회'(10/1) — 같은 실적 발표
  예) '삼성전자 3분기 잠정실적'(매출 중심) ↔ '삼성전자 영업이익 회복'(같은 잠정실적 발표)
- SAME_STORY: 같은 진행 중인 이슈의 다른 단계다. B 가 A 의 결과·후속·다음 회차다.
  예) '마이크론 실적 발표 앞둬'(9/29, 프리뷰) → '마이크론 4분기 실적'(10/1, 결과)
  예) '미국 7월 건설지출' → '미국 8월 건설지출' — 같은 지표의 다음 발표
  예) 'A사 B사 인수 추진' → 'A사 B사 인수 계약 체결' → 'B사 인수 공정위 승인'
  예) 'C사 유상증자 결정' → 'C사 유상증자 발행가 확정'
  예) 'D사 노조 파업 돌입' → 'D사 임금협상 타결'
- DIFFERENT: 두 사건을 잇는 고리가 없다.
  예) '삼성전자 HBM 공급계약' ↔ '삼성전자 분기 배당 결정' — 같은 기업의 별개 사건
  예) 'E사 상한가'(신약 기대) ↔ 'E사 급등'(실적 발표) — 주가 반응만 같고 원인이 다르다
  예) 'SK하이닉스 2분기 실적' ↔ '마이크론 4분기 실적' — 같은 업종이지만 다른 기업의 각자 실적

[판정 규칙]
1. 같은 기업이라는 이유만으로는 SAME_STORY 가 아니다. 같은 계약·소송·제품·인수 건·지표처럼 두 사건을 잇는 구체적인 고리가 주어진 글에 보여야 한다.
2. 주가 반응만 같은 것은 DIFFERENT 다. 급등·급락·신고가·수급 기사끼리는 원인 사건이 같을 때만 잇는다. 원인 사건과 날짜가 같으면 SAME_EVENT, 원인 사건의 후속이면 SAME_STORY.
3. 시리즈 지표의 다음 발표는 SAME_STORY 다. 월간·분기 경제지표(고용·물가·건설지출·수출입 등)와 같은 기업의 정기 실적(직전 분기 → 이번 분기)이 여기에 든다. 같은 회차를 다룬 묶음끼리는 SAME_EVENT.
4. 예고·전망 기사에서 실제 발표로 이어지면 SAME_STORY 다 (프리뷰 → 결과).
5. SAME_EVENT 와 SAME_STORY 가 헷갈리면: 같은 발표의 같은 수치·같은 날을 다루면 SAME_EVENT, 시점이나 단계가 다르면 SAME_STORY.
6. 그래도 애매하면 "B 의 타임라인에 A 가 이전 소식으로 붙어 있으면 독자에게 자연스러운가"로 정한다. 자연스러우면 SAME_STORY, 어색하면 DIFFERENT.
7. 주어진 이름·요약·기사 제목·리드에 드러난 사실로만 판단한다. 외부 지식으로 고리를 지어내지 않는다. 고리의 근거가 없으면 DIFFERENT.

[이유]
한국어 한 줄. 두 사건을 잇는 고리 또는 다른 점을 구체적으로 쓴다.
예) "같은 미국 건설지출 지표의 7월→8월 발표"
예) "같은 기업이지만 공급계약과 배당은 별개 사건"
<!-- prompt:end -->

## 사람 검수 방법

- `human_label` 에 `SAME_EVENT` / `SAME_STORY` / `DIFFERENT` 중 하나를 쓴다. 줄임말 `E` / `S` / `D` 도 된다.
- 판단할 수 없으면 `?` 를 쓰거나 비워 둔다. 채점에서 빠진다.
- `human_note` 는 자유 메모다. 애매했던 이유, LLM 라벨과 다르게 단 이유를 짧게 남긴다.
- 클러스터 하나에 여러 사건이 섞여 있으면 이름(`a_title`/`b_title`) 기준으로 판정하고
  `human_note` 에 `클러스터 오염` 이라고 적는다. 클러스터링 품질 문제를 따로 셀 수 있다.
- 편향 줄이기
  - 검수하는 동안 `band`, `band_population`, `score` 열은 숨긴다. 점수를 보면 판단이 끌려간다.
  - 처음 50행 정도는 `llm_label`, `llm_reason` 열도 숨기고 단다. 그래야 LLM-사람 일치도(kappa)를
    정직하게 잴 수 있다. 나머지는 LLM 라벨을 보며 빠르게 확인해도 된다.
- 저장은 반드시 **CSV UTF-8** 형식으로 한다 (Excel: 파일 → 다른 이름으로 저장 → `CSV UTF-8(쉼표로 분리)`).
  Google Sheets 는 `파일 → 다운로드 → CSV` 그대로 쓰면 된다.
- 행을 지우거나 `pair_id`, `band`, `band_population`, `score` 값을 고치지 않는다. 채점의 가중치가 이 값에서 나온다.
